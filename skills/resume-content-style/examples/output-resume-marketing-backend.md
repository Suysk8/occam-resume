## 项目经历

### 营销优惠中台重构与大促支撑｜2023.03 – 至今｜技术负责人 / 核心开发

**业务背景**：平台券、店铺券、百亿补贴直降等营销玩法直接作用于 C 端下单链路，日均发券约 1200 万张，大促峰值优惠计算 QPS 超过 3 万。原有优惠逻辑散落在交易服务内部，每上线一种新玩法都要改动交易核心代码，需求交付周期长且大促期间变更风险集中。

- **优惠计算引擎抽象**：将 12 种营销玩法归纳为“适用条件 — 优惠动作 — 互斥规则”的统一规则模型，用策略与责任链重构计算流程，新玩法由改动交易代码变为配置化接入，单个玩法上线周期从 2 周缩短到 2 天。
- **高并发防超发方案**：针对补贴爆款券采用 Redis + Lua 原子扣减、本地缓存承接热点 Key、异步落库配合定时对账兜底，2024 年双十一峰值承接 3.2 万 QPS，领券接口 P99 控制在 80ms 以内，超发与少发均为 0。
- **亿级券数据治理**：按用户维度对券记录实施 32 库 128 表分库分表，基于 ShardingSphere 双写平滑迁移 4.6 亿条历史数据，“我的优惠券”列表查询 P99 由 1.2s 降至 120ms。
- **会场选品检索优化**：将会场商品筛选由 MySQL 多表关联改造为 Elasticsearch 倒排检索加冗余宽表，重写查询 DSL 与分片路由后，选品接口平均耗时由 900ms 降至 110ms，支撑单场活动 200 万商品的实时筛选。

### 大促 P0 故障排障与稳定性治理｜2024.11｜故障处理负责人

**业务背景**：2024 年双十一预售开场后，优惠券领取接口大面积超时，下单链路成功率跌至 60%，直接影响 C 端用户领券与下单转化。

- **故障定位与恢复**：通过链路追踪与线程栈分析，定位到热点券 Key 集中落在单个 Redis 分片、并被 MySQL 兜底查询放大的雪崩路径，通过紧急扩容与开启热点降级在 38 分钟内恢复核心链路。
- **根因治理**：引入热点 Key 自动探测与本地缓存兜底，对券模板查询实施多级缓存与请求合并改造，同类热点场景下 Redis 单分片峰值负载下降约 70%。
- **稳定性长效机制**：基于 Sentinel 为营销域 23 个核心接口补齐限流、熔断与降级预案，并沉淀全链路压测与故障演练清单，2025 年 618 与双十一营销域保持零 P0 事故。

### 营销运营 AI 助手｜2025.03 – 2025.08｜后端负责人

**业务背景**：运营配置活动时需要反复查阅玩法规则、历史活动数据与配置手册，新人配错规则导致的线上活动回滚每月数起。项目目标是让运营用自然语言完成规则查询与活动配置校验。

- **RAG 知识问答链路**：基于营销玩法文档与历史工单构建向量检索库，编排检索与大模型调用并加入引用回链，运营规则类问题自助解决率达到 75%，规则咨询工单量下降约六成。
- **配置校验 Agent**：将互斥校验、预算校验等 18 条规则封装为模型可调用的工具，在活动提交前输出风险提示与修改建议，因配置错误导致的活动回滚由每月 3～4 次降至 0～1 次。
