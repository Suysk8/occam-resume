# 简历内容与风格标准

## 元数据

- **类型**：BestPractice / Workflow
- **适用场景**：把原始工作记录 + 目标 JD 转成可交付的简历内容（Markdown）
- **不做什么**：不做 PDF 排版（交给 `resume-ng-latex`）、不做 JD 搜集（交给 `jd-search`）、不编造事实
- **创建/更新**：2026-07-19 创建，2026-09-18 更新（并入口播方法论：关键词闭环、主辅项目结构、奖项归位）

## 核心目标

一份好简历要在面试官扫读的十几秒内，让他形成 **3–5 个关键词印象**，且这些关键词与 JD 要求高度吻合。
整份简历的每一节都服务于这个目标：个人总结抛出关键词，主项目坐实关键词，辅助项目补齐关键词覆盖不到的维度。

默认内容量允许排成 1–1.5 页 A4，不为强行单页压缩表达。工作经历标题字段、项目分段名称和正文强调规则必须传递给 `resume-ng-latex`。

> 本 skill 是 `面试/简历打造/简历版本/实验简历/简历成功标准.md` 的执行版；任一方更新时同步更新另一方。
> 完整示范见 `examples/`：输入 JD 与对应产出简历各一份（示例中人名、公司、数字均为虚构）。

## 输入（缺一则先向用户索取，不得臆造填充）

- **原始记录**：用户提供的工作经历详细记录，是唯一的事实来源。禁止脱离它编造经历、学历、职级、奖项、数字。
- **目标岗位 + JD 关键词**（可由 `jd-search` 收集）：决定内容取舍与措辞侧重——同一段经历，面向"高并发"岗位突出性能与稳定性，面向"AI 工程化"岗位突出 RAG/Agent 落地。关键词只影响选材和用词，不能召唤出原始记录里不存在的事。
- **简历主线 / 个人定位**：必须由用户确认，例如"营销中台与高并发后端""C 端交易系统后端""AI 工程化平台"。如果用户没有明确希望面试官如何认识自己，先主动询问，不得直接根据经历替用户收敛定位。可以结合已有材料给出 2–3 个候选方向帮助用户选择。
- **奖项 / 认证 / 团队规模**（可选）：有则用于工作经历的"技术影响"与个人总结的工程协作条目，没有不补。

## 简历结构（硬约束，顺序不可变）

个人基本信息（姓名、电话、邮箱、求职意向；城市与年限可选，照片可选）→ 个人总结 → 教育经历 → 工作经历 → 项目经历

篇幅配比：项目经历占比最高（约全文一半），个人总结次之，教育经历最简。

**不设独立的"专业技能"章节**：独立技能章节太占篇幅，且没有具体场景支撑，不论怎么写都空洞。技术关键词的 ATS 覆盖由个人总结内的一条"技术栈"关键词行承担；技术深度证据一律放进项目经历的方案描述里。

## 关键词闭环（内容取舍的主轴）

写正文之前先建立这条闭环，它决定了后面所有取舍：

1. **从 JD 反推锚点**：把 JD 的职责与任职要求归并成 3–5 个能力维度（如营销中台、高并发、海量数据、稳定性保障），每个维度对应个人总结的一条锚点词。锚点词用岗位语言，不用自造词。
2. **个人总结抛关键词**：4 条能力总结 + 1 条技术栈，每条以加粗锚点开头，逐条覆盖第 1 步得到的维度。
3. **主项目坐实关键词**：项目经历里的主项目必须能支撑个人总结的前 2–3 个锚点，做到"总结里说的能力，主项目里看得到证据"。
4. **辅助项目补维度**：1–2 个辅助项目，覆盖主项目撑不到的维度，常见组合是"生产事故排障与后续优化"+"AI 相关经历"，也可按 JD 换成架构升级、跨端协作等。
5. **回头自检**：每个 JD 关键要求都能在简历里找到落点；每条个人总结锚点都能在下文找到证据。两边对不上就回到第 1 步调锚点，而不是在正文里硬塞术语。

交付时可附一张"JD 要求 → 锚点 → 证据"的对照表帮用户复核（不进正式简历正文），示例见 `examples/output-resume-marketing-backend.md` 末尾。

## 验收标准

逐条可检查，检查不过就回去改，别交付。

**全局：**

- **关键词闭环成立**：JD 关键要求、个人总结锚点、项目证据三者对得上，不存在"总结里有、正文里查无此事"的锚点，也不存在 JD 核心要求在简历里完全无落点。
- **主线一致**：个人总结、项目取舍和锚点措辞必须共同服务用户确认的个人定位；与主线弱相关的经历可以缩写，不能平均用力。
- **低门槛扫描**：正文以 bullet 呈现，每条只承担一个中心观点；项目"业务背景"可用 1–2 句短段落。允许内容舒展到 1–1.5 页，不通过堆叠术语、并列过多方案或压缩句子制造"高密度"。
- **克制强调（统一视觉中心）**：正文中只有 bullet 开头的锚点短语可以加粗。数字、比例、技术名词、业务背景标签、主要工作以及成果标签及其余正文均用常规字重；章节和项目标题的结构样式由排版模板控制。加粗一多，视觉中心就散了，面试官反而抓不住关键词。
- **XYZ 信息完整性**：成果类 bullet 至少包含 X（做成了什么）和 Z（采取了什么行动）；有真实、可辩护的数字时加入 Y（衡量指标）。不要求每条都具备定量 Y，也不得为套公式编造数字。
- **三部分粒度分工与去重**：个人总结建立"我是谁"的认知，工作经历说明职责范围与协作角色，项目经历提供技术方案和成果证据。同一事实不得在多处以相同措辞和精度重复。
- **数字可辩护**：每个数字要么来自原始记录，要么能在面试中自圆其说（见"数字政策"）。
- **职业化表达**：强调职责、判断、方案和结果，不使用抱怨资源、口语化压缩或可能暗示工程流程不规范的措辞。

**分节：**

- **个人总结**：主要作用是降低面试官阅读门槛，让人一眼看出候选人是谁、做过什么、主线能力是什么，为整份简历的人设铺垫；技术深度留到项目经历展开。
  - 默认使用 4 条能力总结 + 1 条技术栈，每条以简洁的加粗锚点开头；建议依次覆盖业务领域、核心技术能力、生产保障、工程协作，并按 JD 维度替换。
  - 用结论级语言概括能力，可点到代表性中间件或通用技术范式，但不展开故障链路、数据模型、组件组合或实现步骤。
  - 个人总结只保留少量最能支撑定位的规模级信息；恢复时长、改进项数、QPS 数值、单测覆盖率等颗粒度较细的证据应放在对应项目，不能成组复制到个人总结。
  - 末尾保留一条"技术栈"关键词行，只列原始记录中真实使用过的技术，服务 ATS，不承担展示技术深度的职责。控制在一行以内，按"语言 → 框架 → 存储/中间件 → 工程工具"排序。
- **教育经历**：只写学校、专业、学历、时间段，一行写完。按用户偏好紧跟个人总结（不采用"社招放末尾"的惯例）。
- **工作经历**：标题格式为"公司名称｜岗位｜在岗时间"；部门仅在能提供重要组织语境、且不是项目名称时作为可选补充。标题中不得塞入项目名称，项目范围放入下方 bullet。正文写职业画像，通常 1–3 条：
  - 负责过哪些项目（点名即可，细节留给项目经历）；
  - 管理与协作（带多大团队、承担什么管理职责、与哪些团队推进了什么）；
  - 技术影响（获奖、认证、被采纳的方案或沉淀的文档——奖项写在这里，不在项目经历里重复渲染）。
  - **具体的工程建设（监控告警体系、性能优化等）不写在这里**——归入其所属的项目经历。
- **项目经历**：格式"项目名称｜时间｜担任角色"，按时间倒序，取 1 个主项目 + 1~2 个辅助项目。
  - **主项目**：与个人总结锚点吻合度最高的项目，篇幅最大，保留 3–4 条 bullet，把技术方案与能力展开说透。
  - **辅助项目**：各保留 2–3 条 bullet，补主项目覆盖不到的维度（生产排障与后续优化、AI 相关经历、架构升级等）。
  - 每个项目必须分两部分呈现：
    - 业务背景：1~2 句说明项目为什么存在，优先交代业务目标、服务对象、核心场景、业务规模以及要解决的业务问题。技术现状或约束只能作为业务问题的补充，不得把架构、组件或实现方案写成背景主体。
    - 主要工作以及成果：每条 = 加粗锚点 + X（成果）+ 可选的 Y（指标）+ Z（行动）。技术关键词自然融入行动描述，不单列技术栈行。
  - "业务背景："与"主要工作以及成果："是常规字重的分段标签，前后不得添加 `【】`。

## 锚点与加粗规则

锚点是 bullet 开头的短语，用来概括该条的能力主题、关键方案或成果，例如"深耕 C 端业务""高并发触达链路""库存防超卖方案"。锚点必须具体、职业化，并与简历主线一致；个人总结的锚点还要与 JD 维度对得上。

只有锚点短语加粗，冒号后的方案、数字和结果均不加粗：

> **库存防超卖方案**：Redis+Lua 原子扣减、异步落库对账兜底，超卖率 0.12% → 0.003%。

第一条身份概况等不需要锚点的 bullet 可以全部使用常规字重。不得为了满足格式而给每个数字、技术词或整句正文加粗。

## XYZ 公式拆解

- X（成果 / 成就）：说明做成了什么事、完成了什么具体任务，或最终形成了什么业务 / 工程结果。
- Y（衡量指标）：用数字、百分比、金额、规模、时延、吞吐、质量或效率变化证明成果大小。Y 只使用原始记录支持、可在面试中解释的数据。
- Z（具体行动）：说明采用了什么方法、做了什么关键操作或技术决策，避免只写"负责""参与""优化"。

X 与 Z 是成果类 bullet 的必备信息；Y 有可靠数据时优先加入，没有定量数据时可以省略，并用明确的定性结果补足 X。不得把"显著提升""大幅优化"等无证据形容词当作 Y，也不得为了形式完整推算或编造数字。

XYZ 是信息完整性要求，不是固定语序。根据可读性使用"Z → Y → X""X → Z → Y"或"X → Z"的自然表达；每条仍只聚焦一个中心成果。

写作示例：

- 普通写法："负责优化公司网站，提升了访问速度。"
- XYZ 法则写法："通过重构前端代码（Z），将网站平均加载时间缩短了 35%（Y），从而使日活跃用户留存率提升了 15%（X）。"

正式简历中不保留 `(X)`、`(Y)`、`(Z)` 标记，只输出自然、职业化的完整句子；只有 bullet 开头的锚点短语加粗。

## 职业化措辞

| 避免使用 | 风险 | 推荐表达 |
|---|---|---|
| "在无产品经理支持下……" | 容易被理解为抱怨资源不足，或需求缺少专业设计 | "独立承担需求梳理、方案设计、前后端开发、测试上线及部署。" |
| "记录 10 合 1" | 口语化，无法说明数据模型为何变化 | "将原按'用户×券'生成记录的模型调整为按用户聚合券组，使单任务触达记录量降低约 90%。"数字仅在原始记录支持时使用 |
| "先修复、后补测" | 容易被理解为修改生产代码后再补测试，产生工程质量负面联想 | "自研 SonarQube MCP，支持问题定位、代码修复建议及单测生成，缩短存量代码治理周期。" |

优先使用"独立承担 / 主导 / 参与""将 A 模型调整为 B 模型""支持某项能力并带来某结果"等可验证表达。描述客观约束时聚焦采取的判断与行动，不评价组织、流程或协作者。

## 数字政策（硬约束）

原始记录里没有、由推算或合理拓展得来的数字，**必须在交付时逐一向用户说明**：哪个数字是推算的、依据是什么，由用户决定是给出真实具体数字、还是采用 AI 给出的可自圆其说的数字。禁止把推算数字静默混进简历当成事实。

## 反模式（任一出现即不合格）

1. 出现独立的"专业技能"章节；或在个人总结的关键词行之外出现裸名词堆砌。
2. 除 bullet 锚点和结构标题外加粗数字、技术名词、标签或整句正文；或一条 bullet 塞入多个互不从属的方案与结果。
3. 个人总结复制项目中的详细数字、故障链路和技术方案；工作经历出现本应属于某个项目的工程细节。
4. 项目经历缺"业务背景"或"主要工作以及成果"任一部分，给标签添加 `【】`，或把标签加粗。
5. 出现面试中无法展开或自圆其说的数字。
6. 工作经历标题包含项目名称；或"业务背景"以技术架构、组件选型、实现方案为主体，没有说明项目的业务目的与场景。
7. 用户未确认简历主线或个人定位时直接产出定稿；或使用"无产品经理支持""记录 10 合 1""先修复、后补测"等可能产生负面联想的措辞。
8. 为追求单页而过度压缩内容密度，导致句子堆叠、字号过小或阅读节奏紧张。
9. 成果类 bullet 只有职责或行动、没有 X；只有结果、没有 Z；或为了补齐 Y 编造和静默推算数字。
10. 个人总结的锚点在项目经历中找不到证据；或多个项目篇幅平均用力，看不出哪个是主项目。
11. 奖项在工作经历与项目经历中重复渲染；或把奖项当成成果 bullet 的主体而不写做了什么。

## 输出规格

- 产出 Markdown 简历内容文件，按上述结构分节；存放位置听用户指定，未指定则放当前工作目录。
- 若含推算数字，随文附一份"数字来源说明"清单（放简历正文之外），供用户逐条定夺。
- 可选附"JD 要求 → 锚点 → 证据"对照表，同样放在简历正文之外。
- 需要 PDF 时，把定稿内容交给 `resume-ng-latex` 排版；排版环节不得改写内容措辞，内容不合格回到本 skill 修完再排。
